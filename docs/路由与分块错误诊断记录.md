# 路由与分块错误诊断记录

## 已有证据（修复前）

- 运行日志在大量连续热更新后出现 `Router action dispatched before initialization`，随后同一浏览器上下文出现 RSC 网络失败、WritableStream 重复关闭和 `ChunkLoadError`。
- 出错分块属于 Next.js 开发态的 Turbopack 产物：`/_next/static/chunks/node_modules__pnpm_0zrkc9m._.js`，调用方为 `react-server-dom-turbopack-client.browser.development.js`。
- 出错前日志存在一次缺失依赖导致的编译失败，以及短时间内大量 `Compiled` 事件；这会反复替换开发分块图。
- 当前代理规则明确放行 `/_next`，直接请求出错分块返回 `200`、`Content-Type: application/javascript`、`Cache-Control: no-cache, must-revalidate`，说明鉴权代理与安全响应头不是分块失败源头。
- 当前未登录入口的重定向链正常：后台到老板登录、买家端到买家登录、客户入口到买家登录；静态资源请求不发生鉴权重定向。
- `SessionMenu` 只读取路径并请求会话，登录与退出使用整页跳转；`ErrorReporter` 不调用路由 API。两者没有直接发出 App Router action 的代码路径。
- Next.js 16.2.6 的开发服务默认使用 Turbopack，CLI 同时提供 `--webpack` 作为单一、可回退的开发打包模式。

## 根因假设

开发态 Turbopack 在平台反向代理、连续热更新和编译失败恢复的组合下产生瞬时分块图/运行时不一致。浏览器中的旧运行时继续加载或执行另一代模块，导致分块加载失败；同一不一致也会让 App Router action 从未初始化的模块实例发出，因此路由初始化错误是分块运行时不一致的伴随症状，而不是业务页面主动过早导航。

## 对照与回退

- 对照模式：原默认 `next dev`（Turbopack）。
- 稳定模式：仅将开发服务改为 `next dev --webpack`，不改生产构建、不改业务导航、不改鉴权。
- 回退点：移除开发命令中的 `--webpack` 即恢复原模式。

## 固定采集

`tests/e2e/router-chunk-baseline.mjs` 记录所有入口的重定向链，并解析最终 HTML 中的 `/_next/static/**` 资源逐一检查状态和内容类型；可用 `STALE_CHUNK_URL` 复查历史失败分块。
