# 订单流程、支付、配送、账号与全端适配设计

日期：2026-08-28  
状态：老板已确认四部分设计，等待设计文档复核  
资源等级：重型  
实施方案：在现有单仓库系统上分阶段扩展，不重写系统，不替换生产数据

## 1. 目标与范围

本次升级覆盖：

- 客户在商家发货前撤回确认、修改并重新提交订单。
- 商家和客户分别确认订单，报价或订单内容变化后重新确认。
- 在线支付的正式接口占位、现场支付和商家人工确认收款。
- 快递发货、官方查询链接、物流轨迹接口占位。
- 个人送货、送货员独立登录、订单指派与送达凭证。
- 客户、管理员和送货员头像上传与自动切换。
- 主管理员与普通管理员权限分层，订单和仓库管理能力向所有管理员开放。
- 华为、荣耀等主流 Android、鸿蒙兼容模式和 iPhone 的响应式界面。

本次不包含：

- 未取得商户号前启用微信支付或支付宝真实扣款。
- 未取得物流平台账号前抓取自动物流轨迹。
- 删除历史订单、商品、客户、聊天、库存或媒体数据。
- 扩展 AI 商品录入能力。

## 2. 总体方案

继续使用现有 Next.js、TypeScript、SQLite WAL、Docker Compose 和统一网关。订单系统是客户、订单、支付和配送状态的权威来源；仓库系统继续是商品、SKU 和库存的权威来源。

订单不再用一个字段同时表达确认、付款和配送进度。保留 `orders.status` 作为兼容展示和旧接口过渡字段，同时新增三个独立状态字段。所有流转通过单一领域服务完成，API、页面和后台任务不得直接任意写状态。

## 3. 订单状态模型

### 3.1 确认状态 `confirmation_status`

| 值 | 含义 |
| --- | --- |
| `buyer_draft` | 客户正在修改，尚未重新提交 |
| `merchant_review` | 客户已提交，等待商家核价和确认 |
| `buyer_review` | 商家已确认最新内容或报价，等待客户确认 |
| `confirmed` | 双方确认完成 |
| `cancelled` | 发货前取消，保留审计和库存释放记录 |

规则：

1. 新订单提交后进入 `merchant_review`。
2. 商家确认价格、库存和配送方式后进入 `buyer_review`。
3. 客户确认最新订单版本后进入 `confirmed`。
4. 发货前客户可撤回为 `buyer_draft`。撤回后释放尚未最终提交的支付意图，订单版本加一，双方旧确认失效。
5. 客户修改商品、数量、地址或备注后重新提交，再进入 `merchant_review`。
6. 任何影响价格、商品、数量、地址、配送方式或费用的修改都会增加 `order_version`，双方必须确认同一版本。
7. 已发货订单不能撤回、修改或取消，后续售后另立流程，不复用取消入口。

### 3.2 付款状态 `payment_status`

| 值 | 含义 |
| --- | --- |
| `not_required` | 当前阶段尚不需要付款 |
| `unpaid` | 双方已确认，等待付款 |
| `processing` | 支付平台处理中 |
| `paid` | 在线支付验签成功 |
| `manual_pending` | 现场支付等待商家确认 |
| `manual_confirmed` | 商家确认已收到现场款项 |
| `refund_pending` | 退款处理中 |
| `refunded` | 已退款 |
| `failed` | 支付失败，可重新发起 |

支付方式 `payment_method` 为 `wechat`、`alipay` 或 `onsite`。未配置商户号时，后端能力接口返回不可用，前端不展示可点击的微信或支付宝付款按钮。正式接入后必须实现服务端创建支付单、异步回调验签、金额和订单版本核对、幂等处理、退款及对账。客户端返回页面不能作为付款成功依据。

线上支付必须 `paid` 后才允许发货。现场支付可在 `manual_pending` 时安排配送，但订单结束前必须由管理员变更为 `manual_confirmed`。送货员无权确认收款。

### 3.3 配送状态 `fulfillment_status`

| 值 | 含义 |
| --- | --- |
| `not_ready` | 尚未满足发货条件 |
| `ready` | 已满足发货条件，等待安排 |
| `carrier_shipped` | 已交快递 |
| `courier_assigned` | 已指派个人送货员 |
| `out_for_delivery` | 送货员配送中 |
| `delivered` | 快递或送货员标记已送达 |
| `delivery_failed` | 配送失败，等待管理员处理 |
| `received` | 客户确认收货 |
| `cancelled` | 发货前取消 |

配送方式 `fulfillment_method` 为 `carrier` 或 `personal_delivery`。快递发货记录快递公司代码、显示名称、运单号、官方查询地址和发货时间。自动轨迹通过 `LogisticsProvider` 接口接入；未配置供应商时只显示单号和官方查询入口。

个人送货订单必须由管理员指派给一个有效送货员。送货员只能查看自己的订单和完成配送所需的最少客户信息。

### 3.4 订单完成条件

订单只有同时满足以下条件才进入完成状态：

- `confirmation_status = confirmed`；
- `fulfillment_status = received`；
- 在线支付为 `paid`，或现场支付为 `manual_confirmed`。

积分提交、订单完成时间和历史统计统一以该完成条件触发。取消订单释放库存和预留积分；幂等键保证重复请求不会重复释放。

## 4. 客户修改、取消与归档

客户在发货前可执行：

- 撤回确认并修改商品数量、收货地址和备注。
- 重新提交修改后的订单。
- 取消订单。
- 将已取消或已完成订单从自己的列表隐藏。

“删除”采用按用户隐藏，不物理删除订单。`orders.customer_hidden_at` 记录客户隐藏时间；管理员、审计和财务记录仍可查看。订单每次修改在 `order_revisions` 保存完整业务快照，审计日志记录操作者、版本、时间和字段类别，不把敏感地址全文重复写入日志。

## 5. 支付接口边界

定义统一 `PaymentProvider`：

- `capabilities()`：返回是否已配置、支持的支付方式。
- `createPayment()`：根据订单 ID、版本、金额和幂等键创建支付意图。
- `verifyCallback()`：校验签名、商户号、订单号、金额和通知唯一标识。
- `queryPayment()`：服务端主动核对结果。
- `refund()` 和 `queryRefund()`：退款及状态查询。

微信和支付宝适配器在没有凭据时只返回 `NOT_CONFIGURED`，不包含测试密钥或默认商户号。凭据只放服务器环境变量或操作系统凭据存储。

现场支付不是第三方支付适配器。管理员确认收款时必须再次确认金额并写审计记录。

## 6. 物流与送货员

### 6.1 快递

管理员选择快递公司并输入单号。服务端校验长度和字符范围，保存标准化公司代码。客户和管理员都能查看物流摘要；没有物流平台时跳转承运商官方查询页。后续接入快递100或快递鸟时，由后台任务更新轨迹缓存，查询失败不影响订单和发货状态。

### 6.2 送货员账号与页面

新增 `courier` 角色及独立登录入口。送货员页面以手机为主，只显示：

- 分配给当前账号的个人送货订单。
- 订单号、收货人、配送电话、地址、客户备注和导航入口。
- “开始配送”“已送达”“配送失败”操作。

送货员不能查看商品管理、客户聊天、价格设置、仓库、支付配置、其他送货员订单或全量客户资料。服务端按 `assigned_courier_user_id` 再次限制每个请求，不能只依赖前端隐藏菜单。

### 6.3 送达凭证

标记已送达时必须提交以下之一：

- 客户签收确认；
- 现场照片；
- 无法送达的异常原因。

照片限制格式、像素和文件大小，自动纠正方向并压缩，存入受保护的独立媒体目录。仅订单客户、相应送货员和管理员可访问。下载接口每次校验会话和订单权限。

## 7. 账号、管理员与仓库权限

订单系统角色：

- `super_admin`：主管理员，具有全部业务权限和安全配置权限。
- `admin`：普通管理员，具有订单、商品、库存、仓库、消息、发货、收款和物流业务权限。
- `courier`：送货员，仅有本人配送权限。
- `buyer`：客户。

现有唯一 `owner` 数据迁移为 `super_admin`。现有登录会话继续有效；会话查询每次从用户表读取当前角色，因此迁移后的新角色立即生效。权限判断从字符串等值判断改为明确能力，例如 `orders.manage`、`warehouse.manage`、`payments.configure`、`admins.manage` 和 `deliveries.self`。

订单系统管理员进入 `/warehouse` 时，通过现有签名会话桥接映射：

- `super_admin` 映射为仓库 `admin`；
- `admin` 映射为仓库具备完整业务管理能力的角色；
- `courier` 和 `buyer` 不允许进入仓库。

仓库现有 `viewer` 等只读角色不自动提升。只有从订单系统创建并启用的管理员获得完整仓库业务权限。最后一个主管理员不能停用、降级或删除。管理员、送货员、支付和安全配置变更全部写审计日志。

截图中的“无权执行此操作”按请求路径、登录角色、会话桥接和服务端守卫逐层复现，修复根因，并增加普通管理员成功操作与送货员越权失败测试。

## 8. 头像

客户、管理员和送货员可上传、更换自己的头像。新头像保存成功后在同一事务中更新当前头像引用，因此新头像自动成为默认头像。旧头像加入延迟清理队列，确认无引用后删除。

上传要求：

- 只接受经过内容识别的 JPEG、PNG 或 WebP，不只相信扩展名。
- 限制原始文件大小、像素总数和输出尺寸。
- 自动纠正 EXIF 方向、移除不必要元数据并生成统一缩略图。
- 随机存储名，不使用用户提交的路径。
- 头像读取接口按公开范围返回安全缩略图，不暴露存储路径。

订单和仓库界面共用同一账号头像来源，不重复上传。

## 9. 数据库与迁移

预计新增或扩展：

- `orders`：订单版本、三类状态、支付方式、配送方式、双方确认版本、客户隐藏时间。
- `order_revisions`：订单内容快照及修改原因。
- `payment_attempts`：第三方支付意图、幂等键、脱敏平台标识和状态。
- `shipments` 与 `shipment_events`：快递或个人配送记录及轨迹。
- `delivery_assignments`：送货员指派和状态。
- `delivery_proofs`：签收、照片引用或异常原因。
- `user_avatars`：头像文件和当前引用。
- 用户角色和能力映射。

迁移必须独立编号、事务化并可重复执行。先对生产恢复副本连续运行两次，再执行 `quick_check`、外键检查、行数对比和关键订单状态抽样。旧状态映射原则：

- `pending_review` 映射为商家审核阶段；报价待客户确认时映射为客户审核阶段。
- `pending_payment` 映射为双方已确认、未付款。
- `pending_shipment` 映射为已满足发货条件；旧系统无法证明在线支付时保留来源说明，不伪造支付流水。
- `shipped` 映射为已发货但未确认收货。
- `closed` 根据旧记录保留为历史完成或历史取消，并标记迁移来源供审计。

迁移不回写商品或仓库数据，不删除旧字段。兼容期内由领域服务同步维护旧 `status`，待所有接口和报表完成迁移后再单独决定是否移除。

## 10. API 与并发控制

主要接口按资源拆分：

- 客户撤回、修改、重新提交、确认和隐藏订单。
- 管理员确认订单、选择支付/配送方式、确认现场收款、快递发货和指派送货员。
- 送货员读取本人任务、开始配送、提交送达或失败凭证。
- 客户确认收货。
- 支付回调和物流轨迹使用独立内部接口。

所有变更请求携带订单版本或 `If-Match` 等价值。版本不一致返回 `409` 并要求刷新，避免客户修改与商家确认相互覆盖。支付回调、库存释放、积分提交、发货和送达均使用唯一事件键，重复请求返回已有结果。

## 11. 全端响应式设计

使用同一套响应式页面，目标覆盖 Android 8 及以上、鸿蒙兼容模式和当前主流 iOS。重点验收华为、荣耀、小米、OPPO、vivo、三星和 iPhone 常见尺寸，以及系统浏览器、Chrome、Safari、微信和企业微信内置浏览器。

设计约束：

- 手机端宽表格转换为分组列表或订单卡片。
- 主要触控目标不小于约 44 像素，操作区尺寸稳定。
- 弹窗在窄屏切换为底部面板或全屏流程。
- 使用安全区变量适配刘海、挖孔和底部手势区域。
- 支持系统大字体、横竖屏和软键盘弹出，文本不得遮挡或溢出。
- 不依赖悬停完成关键操作。
- 图片上传失败可重试；不支持个别浏览器能力时提供文字或普通文件上传降级。
- 不支持的旧浏览器显示可理解的兼容提示，不能白屏。

## 12. 实施阶段

1. **订单领域基础**：迁移、状态机、版本控制、修改/确认/取消/隐藏和回归测试。
2. **支付、物流与送货员**：支付接口占位、现场收款、快递信息、配送指派和送达凭证。
3. **账号、权限与头像**：能力权限、仓库会话映射、账号管理和头像媒体。
4. **全端界面与发布**：客户、管理员、仓库和送货员响应式页面，隔离预览和生产候选。

每一阶段使用独立分支和拉取请求。后一阶段不得在前一阶段关键测试失败时继续发布。

## 13. 验收标准

### 自动与领域验收

- 所有合法状态转换通过，非法转换返回明确错误。
- 客户修改后双方旧确认失效，重新确认同一版本后才能继续。
- 发货后客户不能再修改或取消。
- 在线支付未付款不能发货；现场支付可以配送但未确认收款不能完成。
- 支付回调、库存、积分和配送事件重复提交不产生重复副作用。
- 普通管理员可完成订单和仓库业务；送货员越权请求被服务端拒绝。
- 头像和送达照片格式、大小、路径和访问权限测试通过。
- 两套数据库 `quick_check=ok`，外键检查无错误，商品和媒体计数不变。

### 浏览器验收

- 客户：下单、撤回、修改、重新提交、确认、付款方式、物流、收货、隐藏订单、头像。
- 管理员：双方确认、现场收款、快递发货、送货员指派、查看凭证、仓库业务和头像。
- 送货员：独立登录、本人任务、导航、开始配送、送达、失败和凭证。
- 桌面和手机视口无关键遮挡、横向溢出、不可点击按钮或软键盘覆盖。
- 华为/荣耀问题在可复现设备或等价浏览器环境中通过回归。

### 发布验收

- 使用全新临时卷完成隔离预览。
- 在生产恢复副本连续执行两次迁移并核对关键数据。
- 独立 reviewer 检查正确性、安全、兼容性、回归和文档。
- 独立 acceptance 按原始需求逐项返回 `PASS / FAIL / BLOCKED / NOT RUN`。
- 老板对最终不可变候选镜像明确批准后才连接生产发布。

## 14. 发布与回滚边界

发布前执行 SQLite 在线备份、媒体备份和 SHA-256 校验，保留当前不可变镜像和已验证恢复点。数据库迁移一旦执行，不允许仅切回不理解新结构的旧镜像。若迁移后失败，发布脚本停止并进入人工恢复流程。

生产数据库、WAL/SHM、头像、签收照片、客户资料、支付/物流凭据和备份不进入 GitHub。任一数据库、库存同步、权限、健康或核心业务检查失败时不得发布。
